Google, Amazon and Microsoft: Three API Estates, and What a Source of

source: linkedin — original ↗
published: 2026-11-20 · status: canonical · expanded from the original post

An API catalog can be consistent and still leave an AI agent guessing about how to get work done.

An API is an interface that lets software request data or actions from another system. A machine-readable source of truth gives teams one authoritative definition of those interfaces, rather than competing descriptions maintained separately.

In plain English: knowing which actions exist is not the same as knowing when to use them, in what order, or at what cost.

That distinction is the useful part of this comparison of Google, Amazon, and Microsoft. The analysis links catalog consistency to a shared source of truth, but finds gaps across all three in support for agent workflows, costs, and lifecycle management.

For teams connecting AI to enterprise backends, I would treat those as separate engineering requirements. Accurate interface definitions are the baseline. Agents also need explicit rules for sequencing actions, limiting spend, and handling interfaces that change or get retired. A cleaner catalog does not supply those rules automatically.

Consider an insurance assistant preparing a claim payment. The catalog might describe how to retrieve a claim and submit a payment. It does not necessarily establish that approval must happen first, or whether retrying a failed request could issue the payment twice.

Making those constraints explicit could prevent a technically valid request from becoming a duplicate payout. That is the gap I would prioritize before giving an agent permission to move money.
